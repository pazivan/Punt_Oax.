# Auditoría de `miguel/integracion-sprint4` frente a `origin/main`

Fecha: 24 de octubre de 2026. Base revisada: `origin/main` (`8730cd8`); integración publicada: `f84f7c2`. También se compararon `origin/ivan/modelo-datos`, `origin/kelly/backend-modelo-datos`, `origin/jonathan/auth-jwt-roles`, `origin/Yareli` y `origin/citlalli/validaciones-auntenticaciones`. Las comprobaciones no hacen merge ni push.

## Resultado y alcance aprobado

- **Iván:** el modelo v1.3 de su rama, con UUID, PostGIS, tablas de usuarios/clínicas/administradores, restricciones y migraciones 001/002 está incorporado; 003 permite registrar usuarios sin nombre. La guía `MODELO_DATOS_Y_AUTENTICACION.md` faltaba en el commit anterior; se recuperó idéntica a la rama de Iván. La semilla 002 con credenciales públicas se omite deliberadamente por defecto. El archivo local `/home/angixs/Descargas/PuntOax_BD_v1_3_postgresql.sql` es una **propuesta diferente**, con otras restricciones; el equipo confirmó que el esquema definitivo de esta integración es el de la rama de Iván. No se incorpora ni se ejecuta ese archivo local.
- **Kelly, PR #23:** registro de usuario, validaciones, normalización del correo, bcrypt, JWT, respuesta sin hash y 409 por duplicado están integrados. Se añadieron defensas ante cuerpos/tipos inesperados.
- **Jonathan, PR #24:** login de usuario, clínica y administrador, emisión/verificación JWT, perfil Bearer y middleware de rol están integrados; `/api/admin/panel-prueba` exige administrador. Se eliminó deliberadamente el secreto JWT de reserva inseguro: ahora es obligatorio configurarlo.
- **Yareli:** se conservaron las pantallas y estilos de acceso y registro; se sustituyeron las respuestas simuladas por peticiones reales, estados de carga y errores. El registro de clínica se señala como no disponible: **no existe endpoint**. El registro de usuario ya no pide nombre ficticio.
- **Citlalli:** se conservó y adaptó `RutaPrivada` de una sesión simulada a perfil consultado con JWT. `/cuenta` acepta los tres roles autenticados; `/admin` exige administrador. No existen paneles por rol: son páginas informativas, no operaciones administrativas.
- **Sprint 3 / main:** el directorio y filtro de clínicas aprobadas permanecen. `origin/main` solo añadió `README.md` desde el ancestro común; una comprobación con `git merge-tree --write-tree origin/main HEAD` no detectó conflictos con el commit publicado.

## Diferencias deliberadas, límites y riesgos antes de integrar

1. **Campos del directorio descartados por decisión del equipo:** Sprint 3 ofrecía `requisitos_generales` y `estado_federativo`; no forman parte del modelo v1.3 de Iván ni de `GET /api/clinicas`. Se retiró de `frontend/src/App.jsx` la referencia obsoleta a `requisitos_generales`. Los requisitos específicos por servicio existen en `clinicas_servicios.requisitos`, pero todavía no se exponen en el directorio. Los campos antiguos no se trasladarán al nuevo volumen: no inventar sus valores ni presentarlo como una migración de registros.
2. **Base Sprint 3 incompatible:** `clinicas` antigua tiene ID entero y columnas/geom distintos. En una base de prueba creada *sin datos reales* con esa estructura, `npm run migrate` falló en 001 con `column "correo_acceso" does not exist` (transacción revertida). El equipo confirmó que las tres clínicas de la instalación Sprint 3 son de prueba y optó por el volumen nuevo para el modelo v1.3; **no se tocó ni borró la instalación antigua**. Si otro entorno necesita conservar registros antiguos, hace falta una conversión diseñada y verificada antes de desplegar allí.
3. **Funciones no implementadas:** registro de clínicas, reservas, OAuth, filtros/proximidad y paneles reales por rol no están disponibles aunque el esquema/guía describa algunas de ellas. La autorización del backend solo está demostrada en la ruta de prueba, no en operaciones de negocio todavía inexistentes. `sessionStorage` es provisional; el equipo debe acordar política de sesión, expiración y despliegue.
4. **Origen de los aportes y PR abiertos:** los commits de Iván, Kelly, Jonathan, Yareli y Citlalli **no son ancestros** de la rama integrada; sus implementaciones fueron adaptadas/copias, no merges que preserven automáticamente la autoría en el historial. Esta auditoría y el PR registran los commits de origen y las adaptaciones concretas (ver abajo); no se atribuyen sus commits a Miguel ni se simula una fusión con `-s ours`. El README de la rama de Iván también describe funciones planificadas, no necesariamente implementadas. La decisión técnica sobre trazabilidad y resolución del conflicto es responsabilidad de esta integración, no una tarea que se delega a los autores. No cerrar ni fusionar PR ajenos como efecto secundario de esta revisión.
5. **Conflicto #23/#24:** ambos PR siguen abiertos y tienen base `ivan/modelo-datos`; GitHub los marca individualmente fusionables a esa base, pero la fusión de las *dos cabezas* (`git merge-tree --write-tree`) da conflicto de contenido en `backend/servidor.js`. **Resolución elegida para este PR:** integrar una sola vez los endpoints de ambos en `backend/servidor.js` y comprobarlos con pruebas reales, sin fusionar posteriormente esos dos PR sobre la integración ni cerrarlos sin autorización. La matriz siguiente deja identificados origen y adaptaciones.

## Evidencia de pruebas (solo entornos aislados)

- `frontend/`: `npm run lint` correcto; `npm run test` 5/5; `npm run build` correcto.
- `backend/`: `PUNTOAX_TEST_DB=1 PGHOST=127.0.0.1 PGPORT=55442 PGDATABASE=puntoax_s4_test_revision PUNTOAX_TEST_API_PORT=3100 npm run test:integration` 1/1. API temporal en 3100 y PostgreSQL temporal en 55442 (tmpfs); registro y hash, duplicados y errores, tres logins, perfil y JWT inválido, denegación de usuario/clínica y autorización de administrador. Los registros de prueba están únicamente en esa base temporal.
- En la base temporal, versiones 001 y 003 presentes; 002 omitida, sin cuentas demo. En otra base sintética v1.3 con `usuarios.nombre NOT NULL`, 001 y 003 se ejecutaron y `nombre` pasó a nullable. En una tercera base sintética Sprint 3, 001 falló como se indica arriba. **No se ejecutaron pruebas sobre los volúmenes existentes ni con sus datos**.
- La prueba automatizada ejercita API/BD y el cliente tiene pruebas unitarias; no sustituye una prueba E2E completa de las rutas React en navegador ni una revisión de seguridad/despliegue.

## Decisión para PR a `main`

**Abrir PR de revisión: sí; fusionar a `main` ahora: no.** El equipo ya decidió adoptar el esquema de la rama de Iván, descartar los dos campos antiguos y usar un volumen nuevo sin borrar el antiguo. La trazabilidad funcional y la atribución se documentan arriba: **no se requiere que los autores resuelvan el conflicto por nosotros**, pero el historial Git original sigue fuera del PR. Antes de fusionar, Miguel debe confirmar si esta atribución documentada es suficiente o si se requiere reconstruir el historial con los commits de origen y una resolución verificada. Un merge simulado contra `origin/main` no tiene conflicto de archivos, pero eso **no** equivale a aprobación funcional ni a preservación de la historia de sus PR.
